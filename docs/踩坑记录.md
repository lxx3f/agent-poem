
# 数据库相关的坑
1. 一些常见的sql语句问题；
2. mysql数据库中的字段名和上层service的参数名不一致，导致运行出错；
3. 由于环境变量配置出错，数据库连接失败（mysql和milvus）；
4. 插入数据时没有检查数据格式，导致插入数据失败；
5. 连接超时问题，长期使用同一个连接导致一段时间后连接超时，需要重新创建连接，后来改成执行完一条语句后立即关闭连接，下次再使用新的连接（也可以考虑使用连接池优化）；
6. pymysql的cursor类型必须显式声明为DictCursor，否则返回的行数据为元组，而不是字典；

# 导入数据的坑
1. 原始数据用的不是标准json格式，需要针对数据进行转换；
2. 数据量太大，运行一次import_data.py需要的时间太长，容易中途失败，需要检查避免重复导入数据，并添加断点记录，下次运行时从上次记录的位置开始导入数据；


# 运行环境相关的坑
1. 本地运行和docker运行的base_url不一样，前者用localhost，后者用容器名，需在docker-compose.yml中添加环境变量进行配置；

# 后端开发遇到的坑
1. 一开始没有设计log，导致后面debug很不方便，大部分时候还是用print调试法；
2. 一开始没有明确规定返回的数据格式，导致有些service返回的是sql查询的结果（元组），有些service返回的是字典，导致api层经常报错，后面规定所有service返回的都是字典，api层统一处理；

# 模型相关的坑
1. 实际运行效果与模型的能力有关，一开始使用的qwen-turbo效果不好，不能理解prompt，甚至很难正常运行一个loop，后来换成qwen-max才能跑通；

# 前端开发遇到的坑
不太懂前端导致push AI的效果也不是很好，每次增加功能和改bug都耗时很长；

# 业务逻辑相关
1. 如何保存用户习惯和偏好：用一个user_agent_memory表保存，每次运行时让agent自动读取该表，根据用户输入判断是否需要更新memory，并保存到数据库中；
2. 如何保存用户当前会话的信息：conversation表增加一个memory字段，用于保存用户当前会话的memory，每次运行时让agent自动读取和更新该字段，并保存到数据库中；
